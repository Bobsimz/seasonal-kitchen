# Implementation Roadmap

## 1. 개발 전략

전체 기능을 고려하여 구조를 잡되, 구현은 의존성이 낮은 영역부터 순서대로 진행합니다.

각 단계는 Swagger DTO, DB migration, 서비스 코드, 테스트를 함께 완료해야 합니다. Swagger만 먼저 만들고 실제 동작을 장기간 미루면 계약과 구현이 어긋날 가능성이 큽니다.

## 2. 단계별 작업

### Phase 0. 프로젝트 골격

- Spring Boot 3, Java 21 프로젝트 생성
- PostgreSQL, Redis 로컬 개발 환경 구성
- Spring Data JPA, Flyway, Spring Security 추가
- springdoc-openapi와 Swagger UI 설정
- 공통 응답과 전역 예외 처리 추가
- local, test, dev 프로필 분리
- Testcontainers 기반 통합 테스트 환경 추가

완료 기준:

- `/swagger-ui.html` 접근 가능
- `/v3/api-docs` JSON 생성
- DB migration 자동 실행
- 공통 오류 응답 테스트 통과

### Phase 1. 기준 정보

- `ingredient`, `season`, `price`, `store` 구현
- 식재료 표준화와 별칭 모델 구현
- 가격 이력과 기준 단위 환산 구현
- KAMIS 수집 client와 batch 구현
- 구매처 참고 가격 API 구현

완료 기준:

- 식재료 목록, 상세, 가격 추이, 구매처 참고 API 제공
- 가격 응답에 기준일, 단위, 출처 포함
- KAMIS 샘플 응답 적재 테스트 통과

### Phase 2. 콘텐츠

- `recipe`, `reel`, `creator` 구현
- 레시피 재료와 조리 순서 구현
- 릴스 영상 메타데이터와 Object Storage 연동
- 좋아요, 댓글, 저장 구현
- 운영자 큐레이션 API 구현

완료 기준:

- 레시피 목록, 상세, 조리 순서 API 제공
- 릴스 피드, 상세, 반응 API 제공
- 관리자 등록 흐름 동작

### Phase 3. 사용자와 인증

- 소셜 로그인과 JWT 구현
- 사용자 프로필과 추천 설정 구현
- 알레르기와 선호도 구현
- 찜과 가격 알림 설정 구현

완료 기준:

- 로그인 후 사용자별 데이터 분리
- refresh token 폐기 가능
- 온보딩 설문 저장 가능
- 찜과 알림 설정 CRUD 동작

### Phase 4. 홈과 검색

- 홈 집계 API 구현
- 통합 검색 구현
- 인기 검색어와 최근 검색어 구현
- Redis 캐시 적용

완료 기준:

- 프론트 홈 화면이 단일 API 응답으로 구성 가능
- 식재료, 레시피, 릴스 통합 검색 가능
- 캐시 무효화 정책 문서화

### Phase 5. 추천과 장보기

- 추천 점수 계산 구현
- 대체 식재료 추천 구현
- AI 구조화 응답 연동
- 장보기 목록과 예상 비용 계산 구현
- 외부 구매처 이동 링크 생성

완료 기준:

- 동일 입력에 대해 가격과 총액을 재현 가능
- AI가 DB에 없는 가격을 생성하지 않음
- JSON Schema 검증 실패 시 안전한 fallback 동작
- 장보기 항목 선택과 해제 가능

### Phase 6. 알림과 분석

- 가격 갱신 이벤트 구현
- DB Outbox 처리 구현
- 앱 내 알림과 푸시 연동
- 검색, 조회, 릴스 완주, 저장, 구매처 이동 로그 적재

완료 기준:

- 가격 조건 충족 시 알림 생성
- 실패 이벤트 재처리 가능
- 행동 로그가 핵심 트랜잭션을 방해하지 않음

### Phase 7. 확장 기능

- 프로모션 관리
- 크리에이터 신청과 검수
- 제휴 링크 전환 추적
- 크리에이터 정산
- 신고와 관리자 운영 화면 지원
- B2B 지표 집계

## 3. 프론트엔드 병렬 작업 순서

Swagger 계약이 안정화되면 프론트는 다음 순서로 mock 데이터를 제거합니다.

```text
OpenAPI TypeScript client 생성
-> 홈
-> 식재료 목록과 상세
-> 가격 비교
-> 검색
-> 레시피
-> 릴스
-> 로그인과 마이페이지
-> AI 추천
-> 알림
```

## 4. 분리 검토 시점

초기에는 단일 서버를 유지합니다. 아래 조건이 발생하면 서비스 분리를 검토합니다.

| 후보 | 분리 검토 조건 |
| --- | --- |
| 가격 수집 batch | 외부 API 수집 실패가 사용자 API에 영향을 줌 |
| 알림 worker | 대량 푸시 발송이 API 응답 성능에 영향을 줌 |
| 추천 worker | AI 응답 시간이 길어 비동기 작업 관리가 필요함 |
| analytics pipeline | 행동 로그량이 핵심 DB 부하를 증가시킴 |
| media processing | 영상 인코딩 작업이 별도 자원을 요구함 |
