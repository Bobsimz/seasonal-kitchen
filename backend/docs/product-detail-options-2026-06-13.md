# 상품 상세 — 옵션 · 상세보기(detailSections) 백엔드 구현 (2026-06-13)

프론트 `products/[producerId]?offer=<offerId>` 상세 화면을 네이버식 구매 플로우로 개편하면서 필요한 백엔드를 정리합니다.
형식·규칙(공통 래퍼 `ApiResponse`, `/api/v1` prefix, 에러코드 UPPER_SNAKE, Flyway `V{n}__`)은 `frontend-api-guide.md`·`conventions.md` 를 따릅니다.

대상 엔드포인트: `GET /api/v1/products/{id}` → `ProductDetailResponse` (`product/controller/ProductController#getProduct`, `product/service/ProductService#getProduct`).

## 화면 변경 요약 (참고)

- 하단바: `장바구니 담기` 단일 → **`찜하기` + `구매하기`**.
- `구매하기` → 바텀시트에서 **옵션 선택 + 수량 + 배송 요약** 후 `장바구니 담기` / `바로 구매`.
- 본문에 **상품 상세정보(접기/펼치기)** 섹션 추가 — **제목+본문 섹션 리스트**(`detailSections`).

---

## 1. 옵션(options) — ✅ 이미 구현됨 (변경 없음)

상품 옵션(규격/variant)은 **이미 구현되어 있습니다.** 프론트는 그대로 소비합니다.

- 테이블: `offer_options` — `db/migration/V24__add_offer_options.sql`
  - `(id PK, offer_id FK→producer_offers, quantity DECIMAL(12,2), unit VARCHAR(30), price DECIMAL(12,2) NOT NULL, sort_order INT)`
- 엔티티: `producer/entity/OfferOption.java`
- 리포지토리: `producer/repository/OfferOptionRepository#findByOfferIdOrderBySortOrderAsc(Long offerId)`
- 매핑: `ProductService#getProduct` 에서 `options` → `List<ProductDetailResponse.OptionResponse{ id, quantity, unit, price }>`

```jsonc
// GET /api/v1/products/401  (data.options 발췌)
"options": [
  { "id": 100, "quantity": 1, "unit": "봉", "price": 4500 },
  { "id": 101, "quantity": 3, "unit": "봉", "price": 12800 },
  { "id": 102, "quantity": 5, "unit": "봉", "price": 20300 }
]
```

**프론트 소비 규칙**
- 옵션 라벨 = `${quantity}${unit}` (예: `1봉`, `1.5kg`).
- 결제금액 = `선택옵션.price × 수량`.
- `options=[]`(옵션 미등록 상품)이면 프론트가 **기준가 단일 옵션**(`{id: offerId, quantity: 1, unit, price: offer.price}`)으로 폴백 → 구매 플로우 항상 동작.
- 시드 예시는 `V24` 패턴을 따라 `INSERT INTO offer_options(offer_id, quantity, unit, price, sort_order) VALUES (...)`.

## 2. 상세보기(detailSections) — ⬜ 신규 구현

상품 상세정보를 **제목+본문 섹션 리스트**로 받아 접기/펼치기로 렌더합니다. 현재 `ProducerOffer.description`(단일 문자열)만 있어 신규 필드가 필요합니다.

### 2-1. 마이그레이션 — `V32__add_offer_detail_sections.sql`

> V31 은 `V31__seed_curated_ingredients.sql` 로 이미 사용 중 — 다음 빈 번호는 V32. (적용 시점에 `db/migration` 최신 번호 재확인)

`offer_options`(V24)와 동일한 패턴(오프셋 정규화 테이블 + `(offer_id, sort_order)` 인덱스).

```sql
CREATE TABLE offer_detail_sections (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    offer_id BIGINT NOT NULL,
    heading VARCHAR(120),                 -- 섹션 제목(선택, null 허용)
    body TEXT NOT NULL,                   -- 섹션 본문
    sort_order INTEGER NOT NULL DEFAULT 0,
    CONSTRAINT fk_offer_detail_sections_offer FOREIGN KEY (offer_id) REFERENCES producer_offers(id)
);
CREATE INDEX idx_offer_detail_sections_offer ON offer_detail_sections(offer_id, sort_order);
```

### 2-2. 엔티티 — `producer/entity/OfferDetailSection.java`

`OfferOption` 스타일(정적 팩토리 `of(...)`, getter only) 일치.

```java
package com.seasonaldining.producer.entity;

import jakarta.persistence.*;

@Entity
@Table(name = "offer_detail_sections")
public class OfferDetailSection {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    @Column(name = "offer_id", nullable = false)
    private Long offerId;
    @Column(length = 120)
    private String heading;
    @Column(nullable = false, columnDefinition = "TEXT")
    private String body;
    @Column(name = "sort_order", nullable = false)
    private int sortOrder;

    protected OfferDetailSection() {}

    public static OfferDetailSection of(Long offerId, String heading, String body, int sortOrder) {
        OfferDetailSection s = new OfferDetailSection();
        s.offerId = offerId; s.heading = heading; s.body = body; s.sortOrder = sortOrder;
        return s;
    }

    public Long getId() { return id; }
    public Long getOfferId() { return offerId; }
    public String getHeading() { return heading; }
    public String getBody() { return body; }
    public int getSortOrder() { return sortOrder; }
}
```

### 2-3. 리포지토리 — `producer/repository/OfferDetailSectionRepository.java`

```java
public interface OfferDetailSectionRepository extends JpaRepository<OfferDetailSection, Long> {
    List<OfferDetailSection> findByOfferIdOrderBySortOrderAsc(Long offerId);
    // 목록 배치 조회가 필요해지면 OfferPhotoRepository.findByOfferIdInOrderBySortOrderAsc 패턴 차용
}
```

### 2-4. DTO — `ProductDetailResponse` 필드 추가

`record` 끝에 필드 1개 + 중첩 record 1개 추가. (옵션 `OptionResponse` 와 동일 위치/스타일)

```java
// ... 기존 필드들 뒤에
        @Schema(description = "상품 상세 섹션(제목+본문) 목록, 없으면 빈 배열") List<DetailSectionResponse> detailSections
) {
    // ... 기존 OptionResponse record 옆에
    @Schema(description = "상품 상세 섹션")
    public record DetailSectionResponse(
            @Schema(description = "섹션 제목", example = "산지 이야기", nullable = true) String heading,
            @Schema(description = "섹션 본문", example = "강원 ○○농가에서...") String body
    ) {}
}
```

### 2-5. 서비스 매핑 — `ProductService#getProduct`

`options` 조회와 동일한 자리에서 한 번 더 배치 조회(상세는 단건이라 N+1 무관).

```java
List<ProductDetailResponse.DetailSectionResponse> detailSections =
        offerDetailSectionRepository.findByOfferIdOrderBySortOrderAsc(id)
            .stream()
            .map(s -> new ProductDetailResponse.DetailSectionResponse(s.getHeading(), s.getBody()))
            .toList();
// new ProductDetailResponse(...) 인자 끝에 detailSections 추가
```

생성자(레코드) 인자 순서에 `detailSections` 를 추가하고, 생성자 주입에 `OfferDetailSectionRepository` 를 더합니다.

### 2-6. 동작 규칙

- 정렬: `sort_order ASC`.
- 비어 있으면 `detailSections: []`. 프론트는 비면 `description` 단일 섹션으로 폴백하므로 안전.
- 숨김(HIDDEN) 상품은 기존 `getProduct` 가드(`STATUS_ACTIVE`)로 이미 비공개 → 상세 섹션도 자동 비노출.
- 미존재/숨김 상품: 기존과 동일하게 `PRODUCT_NOT_FOUND`.

```jsonc
// GET /api/v1/products/401  (data.detailSections 발췌)
"detailSections": [
  { "heading": "산지 이야기", "body": "강원 ○○농가에서 정성껏 기른 봄동입니다..." },
  { "heading": "보관 방법",   "body": "신문지에 싸서 냉장 보관하면..." },
  { "heading": "이렇게 드세요", "body": "데친 후 무침·국 등 다양하게..." }
]
```

### 2-7. 시드(선택)

> ⚠️ 아래 `offer_id` 값(401 등)은 **예시일 뿐**입니다. `producer_offers.id` 는 IDENTITY 자동 생성이라(`V14__seed_producers.sql` 는 id를 명시하지 않음) 401이 실제로 존재한다는 보장이 없습니다. 본 문서 §1·§2-1·§2-6의 `/products/401` 도 동일하게 예시이며, 이는 프론트 mock의 결정적 id 규칙(`producerId*100+idx`)을 빌린 값입니다. 시드를 그대로 복붙하면 `fk_offer_detail_sections_offer` FK 위반이 날 수 있으니, **실재하는 offer를 SELECT로 참조**하거나 시드된 id로 바꿔 주세요.

```sql
-- 예: 첫 번째 봄동 offer 에 상세 섹션 부여 (id 하드코딩 대신 SELECT 로 참조)
INSERT INTO offer_detail_sections(offer_id, heading, body, sort_order)
SELECT o.id, v.heading, v.body, v.sort_order
FROM producer_offers o
JOIN (VALUES
  ('산지 이야기',  '강원 ○○농가에서 정성껏 기른 봄동입니다...', 0),
  ('보관 방법',    '신문지에 싸서 냉장 보관하면...',            1),
  ('이렇게 드세요', '데친 후 무침·국 등 다양하게...',           2)
) AS v(heading, body, sort_order) ON TRUE
WHERE o.ingredient_name = '봄동'
ORDER BY o.id
LIMIT 3;  -- 데모용: 한 offer 에 3섹션
```

## 3. 장바구니 옵션 반영 — ⬜ 보강 (P1)

선택한 옵션을 장바구니 라인에 반영합니다.

- 요청: `POST /api/v1/cart/items` body `{ offerId, qty, offerOptionId? }` (`offerOptionId` 추가).
- 서버: `offerOptionId` 있으면 해당 `offer_options` 행의 **단가(price)** 로 라인 단가 결정 + 라벨(`quantity`+`unit`) 노출. 같은 `offerId` 라도 **옵션이 다르면 별도 라인**(dedup 키 = `offerId + offerOptionId`).
- 응답 카트 라인에 `optionLabel`(또는 `offerOptionId`, `quantity`, `unit`) 포함 권장 → 카트/주문 화면 표기.
- 검증: `offerOptionId` 가 해당 `offerId` 소속이 아니면 `VALIDATION_ERROR`(또는 `OFFER_OPTION_NOT_FOUND`).

> 프론트는 **실 API 경로에서 이미 `offerOptionId` 를 전송**합니다(`endpoints.addCartItem` → `POST /cart/items {offerId, qty, offerOptionId}`). 옵션 없는 상품(기준가 폴백)은 `offerOptionId: null` 로 보냅니다. 따라서 백엔드는 요청의 `offerOptionId` 만 수용/검증하면 됩니다(`AddCartItemRequest` 에 `offerOptionId` 필드 추가).
> 현재 데모(백엔드 off): 프론트가 옵션 단가/라벨을 클라이언트 카트 라인에 스냅샷(`frontend/lib/mock/store.js#addCartItem(offerId, qty, option)`). 백엔드 반영 시 이 폴백은 자동 대체됨.

## 4. 상품 찜 — ⬜ 선택 (P2)

상품(=offer) 찜. `favorites` API에 `targetType=PRODUCT`(또는 `OFFER`) 지원 시 `targetId=offerId` 로 저장하고, 목록 요약(상품명/첫 사진/가격·단위)을 반환합니다. (찜 응답 보강 §3 — `BACKEND-REQUIREMENTS.md`)

> 현재 데모: 데모 스토어 favorites 로 동작. 백엔드 PRODUCT 찜 구현 시 그대로 전환.
